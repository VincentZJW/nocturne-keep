# Chapter Scene Workflow / 章节场景设计工作流

- 状态：**Mandatory / 项目级永久规范**
- 适用范围：所有新章节、扩展区域与 Chapter 01/02 的正式返修
- 配套文件：`chapter_production_checklist.md`、`chapter_qa_standard.md`
- 正式运行入口：保存的 `MainBootstrap` / F5 路线

## 1. 完成定义与永久原则

章节场景必须同时做到“精细”与“符合背景故事”。能够行走、战斗或完成转场，只能证明结构可运行，不能证明正式场景完成。

1. **背景故事优先。** 先理解地点过去的用途、发生的事件、本章揭露的真相、敌人与 Boss 为何在此、前后章节差异，再进行布局和资产设计。
2. **没有资产就先创造资产。** 缺少建筑、门窗、家具、装饰、肖像、机关、拾取物展示、特效或 Boss 房构件时，先制作原创或来源明确的正式像素资产，再搭建正式场景。
3. **概念与实装同等重要。** 概念图、场景设计稿、正式像素资产、保存场景、图层、碰撞、转场和 Main 运行效果必须同时达标。
4. **每章拥有独立视觉身份。** 建筑语言、颜色体系、材质、光源、环境叙事、区域节奏和标志物不能只是上一章换色或复制。
5. **Main/F5 是最终权威。** 工具场景、F6、编辑器预览和截图只能辅助验证，不能代替正式章节路线。

以下内容不能作为正式场景资产长期交付：Line2D 门窗、空画框、简单 Polygon2D 建筑、纯色矩形家具、白线武器、红色曲线拱门、大面积空墙、只有砖墙/地板/平台的房间。灰盒仅可存在于明确标注为 `prototype_only` 的已批准灰盒阶段，并必须在正式验收前替换。

## 2. S0：项目与章节审计

开始任何修改前，必须读取 `project.godot` 并沿真实引用检查：

1. `run/main_scene`、Main/Bootstrap、Chapter Registry 与 Debug Start Profile；
2. 上一章出口、本章入口、下一章占位入口；
3. 本章已有场景、房间、资产、共享资产和旧占位资产；
4. 当前 Camera、HUD、检查点、重生、碰撞层、图层和转场系统；
5. 本章剧情定位、敌人体系、Boss 关系、章节节奏和标志性意象；
6. 当前 Output/Debugger、缺失资源、旧路径和 Inspector Override。

S0 必须输出：章节场景清单、每区剧情/玩法功能、美术关键词、`new/reuse/adapt` 资产缺口、开发顺序、风险和本阶段停止点。完成审计后才能进入设计。

## 3. S1：场景与环境叙事设计

按章节实际内容设计起点、前/中段区域、安全屋、检查点、剧情区、高压战斗区、Boss 前室、Boss 房、奖励区和章节出口；不要求机械地拥有全部类型，但存在的区域必须有独立用途。

每个区域必须回答：

1. 曾经是什么地方；
2. 发生过什么以及为何破败；
3. 当前敌人为何存在于此；
4. 章节专属物件、光源和视觉记忆点是什么；
5. 如何服务探索、战斗、教学、解谜、休息或剧情；
6. 如何逐步揭示本章真相与 Boss；
7. 与前后区域在轮廓、材质、密度和色彩上有何区别。

推荐产物：房间路线图、环境叙事矩阵、资产需求表和层级草图。

## 4. S2：章节环境资产先行

章节专属资产归属到实际需要的目录：

```text
res://chapters/<chapter_id>/assets/
├── environment/
├── props/
├── doors/
├── backgrounds/
├── foregrounds/
├── fx/
├── interactables/
└── concept_art/
```

目录按需创建，不为不存在的内容制造空目录。资产必须体现建筑厚度、门板/门框、拱顶、柱体、家具、光源、小型装饰、场景叙事物件和章节标志物；使用硬像素边缘、最近邻采样、项目统一比例和明确透明边界。每项资产记录原创/复用/许可来源。共享资产只在确有跨章节价值时进入 `shared/`，并说明复用与适配理由。

S2 退出条件：正式场景的关键构件不再依赖占位几何，资产可被保存场景真实引用，且在目标分辨率下不破坏角色和战斗可读性。

## 5. S3：使用正式资产组装场景

每个主要画面应拥有：

- Background：远景、深度与章节色调；
- Architecture：墙体、门窗、柱体与固定建筑主体；
- Ground/Platforms：视觉和碰撞一致的行走面；
- Props Behind / Midground：中型陈设和环境叙事；
- Gameplay：Player、Enemies、Interactables、Pickups；
- Foreground：受控遮挡与空间纵深；
- Lighting/Atmosphere：不吞没危险提示的光效与氛围。

每个主要 Viewport 原则上至少有一个主建筑结构、2–4 个中型道具、3–8 个小型装饰、一个明确光源区和一个章节叙事信息点。该密度是检查起点，不是机械铺量指标；资产不得重复堆满、制造虚假平台/门/危险或遮挡攻击前摇。

## 6. S4：图层、碰撞与路径

检查 Background → Architecture → Ground/Props Behind → Player/Enemies/Interactables → Foreground → HUD 的绘制关系。玩家、敌人、武器、投射物和关键提示不能被地面填充、门板或装饰错误遮挡。

碰撞与路径必须满足：

- 视觉结构与物理结构一致，无隐形墙和虚假地面；
- 门开启后正确解除阻挡，Dash 不能穿越实体墙；
- 必经平台、楼梯和出口在正式能力条件下可达；
- 敌人不会卡入平台、楼梯或装饰；
- 前景不会长期遮挡玩家、Boss 或落脚点；
- Camera Bounds、出生点、检查点和重生位置合法。

## 7. S5：转场与性能

房间、楼层、Boss 和章节转场必须测试资源首次加载、SpriteFrames、Shader、音频、节点 `_ready()`、Camera Bounds、节点释放、隐藏房间处理和 Debug HUD 开销。

不得单纯延长黑屏掩盖卡顿。需要时在黑屏中分阶段初始化、预加载关键资源、避免同帧加载/卸载/传送/Camera 重置，并关闭非当前房间的 process/physics_process。任何性能优化声明必须保留优化前后的可复现实测数据。

## 8. S6：Main 集成与场景 QA

读取真实 `run/main_scene`，追踪 Bootstrap、章节路由和入口。正式入口、主要房间、楼层切换、检查点、Boss 区、奖励区和下一章入口必须可通过正常路线或合法 Debug Chapter Start 在 F5 中抵达。

Main 证明至少包括：

- 保存场景引用最新章节资产，无实例级旧资源 Override；
- Player、HUD、Camera、重生与章节状态不重复、不丢失；
- 保存并重开项目后引用仍有效；
- Debug UI 关闭后仍正常；
- Output/Debugger 无红色错误；
- `docs/qa/` 中保存实际命令、路线、截图/日志与人工验收项。

场景质量状态只能使用 `PASS`、`PARTIAL` 或 `FAIL`。仍像灰盒、缺少正式资产、与故事脱节或只在 F6 中可见时必须是 `FAIL`。

## 9. 固定场景交付报告

```markdown
## Chapter X 场景开发报告

### 本章场景主题
### 背景故事与环境叙事目标
### 本章新增 assets
### 本章复用 assets
### 本章资产路径
### 本章主要场景清单
### 每个场景的视觉定位
### Main 集成情况
### F5 测试方法
### 场景切换流畅度检查
### 图层与碰撞检查
### Output / Debugger
### 当前完成度
### 已知不足
### 下一步建议
```

报告必须明确回答：“按 F5 进入 Main 后，在哪里、沿什么路线、通过什么操作测试本章场景质量？”并提供 `chapter_id`、`spawn_id`、路线、应观察结果和 QA 证据路径。
