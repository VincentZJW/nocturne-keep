# Chapter QA Standard / 章节强制QA标准

- 状态：**Mandatory / 不可由普通任务隐式跳过**
- 适用范围：章节场景、人物、Boss、转场、奖励和 Main 集成
- 证据目录：`docs/qa/<chapter_or_milestone>/`

## 1. 状态定义

只能使用以下状态：

- `PASS`：要求已在正式保存内容与 Main/F5 中验证，证据可复现；主观美术项需注明是否已经用户人工验收。
- `PARTIAL`：有可运行/可审查产物，但仍缺明确要求、证据或人工验收；不能写成完成。
- `FAIL`：存在阻断项、正式路线不可用、质量仍为占位级或测试失败。

不得用“基础完成”“框架完成”“后续可优化”“像素风需要简化”“理论上可运行”“已创建占位版本”等措辞掩盖 `PARTIAL` 或 `FAIL`。

## 2. 直接 FAIL 条件

1. 正式场景仍像灰盒或由简单几何体主导；
2. 大面积空墙，区域缺少用途和章节身份；
3. 人物仍像几何小人，武器仍像线条；
4. 原画精细但正式 Sprite/场景粗糙；
5. 动画闪回旧帧、武器变形或关键动作缺失；
6. Boss Phase 2 只换色、加粒子或调速度；
7. 新资源没有进入 Main，只有 F6/独立测试证据；
8. 正式运行仍引用旧资源或错误 Inspector Override；
9. Output/Debugger 有红色错误、缺失资源或解析失败；
10. 未测试图层、碰撞、可达性、死亡/奖励/转场等批准范围；
11. 使用来源不明、未授权或不可追溯资产；
12. 报告声称执行了没有保存命令和结果的测试。

## 3. 场景 QA

| 项目 | 验收问题 | 必需证据 |
|---|---|---|
| 背景故事一致性 | 建筑、陈设、敌人与章节真相一致吗？ | 区域叙事矩阵 + Main截图 |
| 环境资产真实性 | 是否由正式章节资产构成而非占位几何？ | 资产清单 + 引用路径 |
| 场景精细度 | 主画面是否具备结构、道具、光源和叙事点？ | 代表性原始分辨率截图 |
| 房间区分度 | 不同区域是否能不靠标题辨认用途？ | 多区域对照截图 |
| 环境叙事 | 是否能读出过去用途、事件与Boss线索？ | 叙事物件位置记录 |
| 图层 | 角色/敌人/攻击是否未被错误遮挡？ | 战斗截图 + 节点/z_index审计 |
| 碰撞与可达 | 视觉地面、平台、门和物理一致吗？ | 路线测试/自动检查 |
| 转场 | Player/HUD/Camera/状态是否稳定？ | F5路线日志 |
| 性能 | 是否无首次加载卡顿掩盖、无无效处理？ | 优化前后实测（如适用） |
| Main集成 | 正式Bootstrap是否真实可达？ | `chapter_id`/`spawn_id` + F5证据 |

## 4. 人物 QA

| 项目 | 验收问题 | 必需证据 |
|---|---|---|
| 概念原画 | 正式概念、侧视、剪影、武器/姿态是否存在？ | 仓库路径 + 预览 |
| 剪影 | 原始尺寸与黑色剪影能否识别岗位？ | 对照板 |
| 正式Sprite | 是否保留概念识别点和比例？ | Sprite预览 + Main截图 |
| 材质与结构 | 头/躯干/四肢/服装/护甲是否分明？ | 原始分辨率检查 |
| 武器/道具 | 刃、柄、结构、方向是否清楚且动画连续？ | idle/attack/turn截图 |
| 动画 | 移动、转身、攻击三段、受击、硬直、死亡是否完整？ | 动画清单 + 运行捕获 |
| 战斗适配 | Hitbox、Hurtbox、朝向、锚点是否匹配？ | 自动测试 + 调试证据 |
| Main集成 | 正式Encounter是否引用最新资源？ | PackedScene/SpriteFrames路径 |
| 旧资源清理 | 运行时旧路径是否为0且可恢复？ | `rg`/引用审计结果 |

## 5. Boss QA

| 项目 | 验收问题 | 必需证据 |
|---|---|---|
| Phase原画与剪影 | 每个Phase是否结构上不同？ | Phase对照图 |
| 武器/能力 | 是否独立于普通敌人且全动画一致？ | 设计图 + 攻击截图 |
| 入场与对白 | 是否形成章节级身份且能在Main触发？ | F5捕获/日志 |
| 攻击读招 | Windup/Active/Recovery和视觉判定一致吗？ | 关键帧 + Hitbox证据 |
| 变身 | 是否真实改变至少三项结构而非换色？ | 转换序列 |
| 受击/Stagger | 是否不破坏正式AI与阶段？ | 回归测试 |
| 死亡 | 是否完整、可读且正确清理？ | 死亡序列 |
| 奖励/出口 | 是否在Boss后完整接续且可持久化？ | Main路线证据 |
| Main集成 | Boss房正式实例是否无旧覆盖？ | 场景路径 + F5截图 |

## 6. Main/F5 强制证据

每个正式验收必须写明：

- `project.godot` 的实际 `run/main_scene`；
- 正式章节场景路径；
- `chapter_id` 与 `spawn_id`（若使用合法 Debug Start）；
- 从出生点到目标的路线与操作；
- 目标节点/PackedScene/SpriteFrames路径；
- 应观察的场景、敌人、Boss、动画、奖励或转场结果；
- 正常 F5 路线是否仍有效；
- Debug配置是否在测试后恢复；
- Output/Debugger结果；
- 截图、视频、日志或报告的仓库路径。

固定验收问题：

> 这些内容在独立测试场景完成了，那我按 F5 进入 Main 后具体在哪里、通过什么操作能够测试？

如果不能给出可复现答案，Main 集成状态不得为 `PASS`。

## 7. 测试层级与证据诚实性

1. 精确 Godot 4.7.1 import/parse：资源和脚本基础有效性；
2. 自动测试：确定性逻辑、引用、数值和状态契约；
3. 独立场景：动画、碰撞和单体行为排查；
4. 组合/Encounter：多角色、平台和重置；
5. Main/F5：正式路由、实例、HUD、Camera、奖励和转场；
6. 人工验收：美术质量、读招、公平性、氛围与玩家感受。

自动测试不能证明美术已获用户认可；截图存在不能证明整个流程可玩；F6通过不能证明Main通过。报告必须把自动结果、视觉自检和用户人工验收分开写。

## 8. QA报告模板

```markdown
## Chapter X 强制QA报告

### 范围与正式入口
### 场景QA
### 人物QA
### Boss QA
### Main/F5测试路线
### 旧资源引用审计
### Output / Debugger
### QA证据路径
### PASS / PARTIAL / FAIL汇总
### 需要用户人工验收的项目
### 未通过项与停止点
```

每行重要验收项建议使用：

| 项目 | 状态 | 证据 | 备注/人工验收 |
|---|---|---|---|

未关闭的阻断 `FAIL` 存在时，章节或对应里程碑不得标记完成。
