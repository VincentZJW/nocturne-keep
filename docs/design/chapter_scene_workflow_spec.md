# 章节场景强制工作流规范

- 状态：**Mandatory / repository policy**
- 适用范围：Chapter 03、Chapter 04、Chapter 05、Chapter 06 的全部正式场景开发，以及 Chapter 01、Chapter 02 的任何正式返修
- 执行入口：根目录 `AGENTS.md`
- 验收入口：F5 实际 `MainBootstrap` 流程与 `docs/qa/` 证据

## 1. 目的与完成定义

章节场景的最高优先级是：

1. 场景达到正式、精细、可复用的像素美术质量；
2. 场景准确服务本章背景故事、叙事氛围、关卡主题和玩法节奏。

“能够运行”不等于“场景完成”。以下任一情况存在时，不得将正式场景里程碑标记为完成：

- 大面积空墙、纯色背景、矩形平台或基础砖墙构成了主要视觉内容；
- 门、窗、拱门、画像、家具或武器仍由线条、空框、Polygon 或简单色块长期代替；
- 场景与章节故事、敌人来源或 Boss 关系没有可读联系；
- 整章只复制同一种房间、砖墙或装饰，区域用途无法辨认；
- 正式资产只存在于工具/预览场景，没有进入保存的 Main 路线；
- 缺少图层、可达性、碰撞、切换、引用或 Output/Debugger 验证；
- 场景仍明显像灰盒或占位图。

灰盒仅允许用于名称和范围都明确的“原型/灰盒里程碑”。灰盒交付必须标注 `prototype_only` 或等价状态、说明替换计划，并且不能作为正式环境美术完成证据。

## 2. 六道顺序门槛

正式章节开发必须按顺序通过下列六道门。未通过上一道门时，不进入下一道正式交付。

| Gate | 必须完成的工作 | 必须留下的产物 | 退出条件 |
|---|---|---|---|
| 1. 章节审计 | 分析剧情、主题、建筑、敌人、Boss、节奏、标志性元素、章节差异和资产复用 | 章节场景设计摘要、环境关键词、资产需求清单 | 每个区域的叙事与玩法目的均可说明 |
| 2. 资产先行 | 审计现有资源；缺什么就创建什么；核对原创性/授权来源 | 章节本地正式像素资产、资产清单、来源与复用记录 | 正式场景所需关键物件不再依赖占位图 |
| 3. 正式组装 | 用正式资产构成背景/中景/前景和具有用途差异的房间 | 保存的章节 `.tscn`、必要资源和明确节点层级 | 场景不空、不粗糙，玩法轮廓清楚 |
| 4. 环境叙事 | 让建筑、陈设、光源、破败和特殊物件共同讲述章节故事 | 区域叙事矩阵、关键叙事物件位置 | 玩家无需文档也能读出地点用途和事件痕迹 |
| 5. Main 集成 | 接入实际 `MainBootstrap`/F5 路线与正式章节入口 | 保存的路由/章节引用、可重复的 F5 测试方法 | F5 正式流程能抵达并完整游玩该场景 |
| 6. QA 验收 | 检查视觉、主题、图层、可达性、碰撞、切换、引用和运行错误 | `docs/qa/` 报告、截图/日志、开发日志结果 | 所有阻断项关闭；主观质量项明确交由人工验收 |

## 3. Gate 1：章节场景审计与设计拆解

开始制作前，必须读取本章已有剧情、关卡、敌人、Boss、相邻章节和世界观文档，并回答：

1. 本章在整体剧情中的作用是什么？
2. 核心场景主题和情绪曲线是什么？
3. 美术关键词、时代背景和建筑语汇是什么？
4. 本章敌人的形态与行为为何适合此地？
5. Boss 与空间、历史和章节真相有什么关系？
6. 探索、战斗、解谜、教学、压迫、休息和终局段落如何分布？
7. 哪些视觉元素必须成为本章记忆点？
8. 与上一章、下一章如何在轮廓、材质、色彩、光源和空间节奏上区分？
9. 哪些共享资产可以合理复用，哪些章节资产必须新建？
10. 每个区域对玩家有什么可感知的用途？

审计产物至少包含：

- 章节场景设计摘要；
- 5–10 个本章环境关键词；
- 房间/区域清单及其叙事、玩法和视觉定位；
- 缺失资产清单，标注 `new`、`reuse`、`adapt`；
- 资产风险：授权、比例、调色、图层、动画或性能风险。

推荐使用以下环境叙事矩阵：

| 区域 | 曾经用途 | 发生过的事件 | 当前威胁 | 章节/Boss线索 | 玩法用途 | 所需资产 |
|---|---|---|---|---|---|---|
| 示例 | 王室宴会厅 | 最后一场舞会中断 | 诅咒侍从 | 被划毁的家徽 | 中段战斗 | 餐桌、银器、帷幕、家徽 |

## 4. Gate 2：正式资产先行

不存在合适资产时，必须先创建资产，再搭建正式场景。禁止用几何块、线条、空画框或纯色轮廓替代正式美术并长期留在 Main。

资产范围包括但不限于：

- 建筑结构件：墙面模块、门框、门扉、拱门、柱子、壁龛、窗户、护栏；
- 陈设：桌椅、床、柜、武器架、雕像、烛台、器皿、残骸；
- 叙事物：帷幕、挂画、旗帜、纹章、祭坛、档案、处刑/仪式痕迹；
- 玩法物：机关、交互装置、检查点、可破坏/危险物、拾取物展示台；
- 专属物：Boss 房构件、章节符号、特殊光源、环境 FX、章节 UI。

正式像素资产必须：

1. 具有明确用途和可辨轮廓；
2. 与章节配色、材质和年代一致；
3. 使用清晰像素边缘、最近邻采样和项目统一比例；
4. 可由保存场景直接引用，而非只存在于生成脚本或截图；
5. 记录为原创、项目内复用或具有明确许可来源；
6. 避免随机单像素噪点和无意义细节；
7. 在目标窗口中不抢夺角色、敌人、攻击和平台的可读性。

### 4.1 章节目录约定

章节独有内容应位于：

```text
res://chapters/chapter_xx_slug/
├── assets/
│   ├── environment/
│   ├── props/
│   ├── doors/
│   ├── portraits/
│   ├── weapons/
│   ├── pickups/
│   ├── fx/
│   └── ui/
├── scenes/
├── docs/
└── resources/
```

不存在内容的空目录不必预建；首次新增对应资产时创建。跨章节共享内容可以位于 `shared/` 或现有全局目录，但章节资产清单必须说明：来源、复用原因、是否重新调色/适配，以及为何不应归属章节本地。

## 5. Gate 3：用正式资产组装场景

每个正式场景至少需要：

- **背景层**：建立地点、深度、远景与章节色调，不覆盖交互角色；
- **中景层**：承载建筑主体、门窗、墙面叙事和主要陈设；
- **Gameplay 层**：碰撞地面、平台、玩家、敌人、机关、拾取物与可读边界；
- **前景层**：提供深度但控制遮挡，关键战斗区不得长期盖住角色或攻击；
- **光效/氛围层**：强化主题，不得制造模糊或掩盖危险提示。

章节内至少应区分适用的区域类型：前段探索、中段战斗、特殊事件、精英区、安全屋/检查点、Boss 前室、Boss 房和结尾转场。不是每章必须机械地拥有全部类型，但实际存在的区域必须在布局、资产组合、光源、破败程度或空间节奏上具有独立身份。

正式组装验收重点：

1. 玩家能从画面理解可行走地面、可达平台、门和交互物；
2. 敌人轮廓、前摇、投射物和 Hitbox 方向不被背景吞没；
3. 前景不会持续遮挡玩家、Boss 或关键落脚点；
4. 装饰不制造虚假平台、虚假门或虚假危险；
5. 装饰密度有节奏，不靠复制单一道具填满整章；
6. 每个区域都能通过资产组合识别其功能，而非只靠标题文字。

## 6. Gate 4：场景服务背景故事

环境叙事必须回答五个玩家层问题：

1. **这里曾经是什么？** 建筑类型、家具和动线说明旧用途。
2. **这里发生过什么？** 破损、封锁、遗留物和光源变化说明事件。
3. **为什么这些敌人在这里？** 布阵、装备、巡逻和驻守目标与地点一致。
4. **Boss 为什么属于这里？** Boss 房尺度、象征、机关和遗物与其身份一致。
5. **玩家接近了什么真相？** 区域顺序逐步加强线索，而非一次性用文字解释。

叙事信息应主要通过可视资产和空间组织表达；字幕、房间标题和对话只能补充，不能替代场景本身。

## 7. Gate 5：接入 Main 正式流程

正式资产和场景必须进入 F5 实际启动流程。验收前应读取 `project.godot` 的 `run/main_scene`，再追踪 `MainBootstrap`、章节路由和章节入口，不能根据文件名猜测。

Main 集成必须证明：

1. 正式章节路径引用最新保存场景和资产；
2. 新内容在正常章节路线或合法 Debug Chapter Start 中可抵达；
3. 进入/退出、检查点、重生、Camera、HUD 和 Player 状态保持正确；
4. 关闭 Debug UI 后场景仍可玩；
5. 保存并重新打开项目后引用仍存在；
6. 工具场景或独立测试场景的成功不能替代 Main 验收。

## 8. Gate 6：测试与 QA

### 8.1 必测项目

- 视觉完整性：没有被误当作正式资产的占位几何；
- 主题一致性：色彩、材质、时代、建筑和章节故事一致；
- 图层：背景/中景/Gameplay/前景关系正确，无角色错误遮挡；
- 可达性：正式移动能力能到达所有必经路线、平台和出口；
- 碰撞：视觉地面与物理地面一致，无穿墙、卡死或虚假碰撞；
- 切换：房间/楼层/章节转场平顺，Player/HUD/Camera 不重复或丢失；
- 资源引用：无缺失、旧路径、孤立正式资源或错误过滤；
- Main：F5 路线真实可达，不能只运行房间本身；
- Output/Debugger：无红色脚本、资源、节点或导入错误；
- 战斗可读性：角色、敌人、危险、交互和平台在目标分辨率清楚。

### 8.2 QA 证据

相关证据应保存到 `docs/qa/chapter_xx_<milestone>/`，至少记录：

- 精确 Godot 4.7.1 命令和退出结果；
- F5/Main 路由和测试起点；
- 代表性截图，覆盖不同区域、层级和战斗场景；
- 图层、可达性、碰撞、切换、引用和错误检查结果；
- 主观人工验收项，不把“自动截图存在”误写成“美术质量已获用户认可”。

性能判断必须先保留基线，再进行有目标的优化和复测；不能仅凭“使用了较少节点”宣称已优化。

## 9. 固定禁止事项

1. 没有资产就用几何块凑正式场景；
2. 用占位图长期代替正式资产；
3. 只做结构，不做正式美术；
4. 做完场景却不接 Main；
5. 只在独立测试图中可见；
6. 明显空洞粗糙却报告“已完成”；
7. 场景与背景故事脱节；
8. 只复制同一道具铺满整章；
9. 章节独有资产散落在无归属的全局目录；
10. 不执行 QA 就结束。

## 10. 每次章节场景工作的执行模板

1. 读取本章剧情、关卡、敌人、Boss、相邻章节和现有资产；
2. 输出主题、美术关键词和环境叙事目标；
3. 列出缺失资产并决定 `new/reuse/adapt`；
4. 优先创建缺失的正式资产并归档至章节目录；
5. 用正式资产组装保存场景；
6. 接入 Main 正式章节路径；
7. 使用准确 Godot 4.7.1 执行导入、自动测试和 F5/Main 测试；
8. 保存视觉与技术 QA 证据；
9. 对照六道门决定 `complete`、`in progress` 或 `blocked`；
10. 若画面仍像占位图，继续打磨，不得标记完成。

## 11. 固定交付报告

每个章节场景里程碑必须至少使用以下结构：

```markdown
## Chapter X 场景开发报告

### 本章场景主题
### 背景故事与环境叙事目标
### 本章新增 assets
### 本章复用 assets
### 本章资产路径
### 本章主要场景清单
### 每个场景的视觉定位
### Main 集成情况
### F5 测试方法
### 场景切换流畅度检查
### 图层与碰撞检查
### Output / Debugger
### 当前完成度
### 已知不足
### 下一步建议
```

报告必须明确、可操作地回答：

> 这一章如果我按 F5 进入 Main，应该如何测试本章场景质量？

回答至少包括实际启动路径、合法章节起点、行进路线、应观察的场景记忆点、战斗可读性、图层/碰撞/切换检查和 QA 证据路径。

## 12. 审批与范围控制

- 本规范不授权自动开始下一章，也不扩大当前已批准里程碑；仍执行“一项里程碑、测试、提交、停止等待批准”。
- 新建资产、正式组装、Main 集成是同一正式场景里程碑的质量门，但具体章节范围必须先获用户批准。
- 如果缺少剧情或关键视觉决定，先记录待确认项；不得用无关通用场景替代章节身份。
- 任何章节未通过本规范时，状态只能是 `in progress` 或 `blocked`，不能写 `complete`。
